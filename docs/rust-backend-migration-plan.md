# New API 后端 Rust + Axum 全过程重写计划书

## Context

用户要求将 https://github.com/xiaocongyu66/new-api 的后端完整重写为 Rust，Web 框架指定 Axum，并要求先形成全过程计划书，后续严格按计划执行。仓库已克隆到 `/root/newapi`。目标是替换现有后端而不是只提供代理外壳；保留前端、现有业务语义和可验证的数据兼容性。

当前状态：2026-11-02 已批准；P0 进行中，P1–P10 未开始，尚未编写 Rust 实现。上游基线 commit：`17970da4571e81308f176a0e61a38276e5771606`。Rust 工具链已存在。旧 README 与源码存在偏差，所有兼容判断以当前源码及可执行契约测试为准。`apps/api/main.go` 使用 Fiber adapter，不能按旧文档描述的 Gin 架构推断现状。

## 1. 执行约束与变更控制

1. 批准后在 `/root/newapi-rs` 初始化独立 Git 仓库，将本计划落地至 `/root/newapi-rs/docs/rust-backend-migration-plan.md`，作为唯一主计划；不以聊天记录代替计划。`/root/newapi` 只读参考，禁止向 `xiaocongyu66/new-api` 推送。不继承原仓库 origin，不在原仓库提交或改写文件。用户已授权在 `gh` 当前登录账号下创建公开 GitHub 仓库 `newapi-rs`，并向该新仓库提交、推送开发分支用于 CI；执行前核对身份与同名仓库状态。
2. 严格按照 P0→P10 顺序推进。每阶段必须有交付物、验证证据和独立验证结论；未通过不得标记完成或跳至依赖阶段。
3. 维护阶段状态及逐项接口/模块台账。状态仅允许：未开始、进行中、受阻、已验收。阶段记录包含源码基线、变更文件、执行命令、结果及遗留问题。
4. 不默默缩减范围，不用成功空响应模拟未实现功能，不将转发回 Go 算作 Rust 重写完成。不为赶进度移除失败测试、弱化鉴权或忽略计费差异。
5. 新发现的接口和业务进入台账。涉及技术选型、支持范围、数据结构、阶段顺序或兼容性目标变化时，先记录原因、影响和修订内容，征求用户确认后执行。
6. 保留 Go 实现和测试直至最后退役阶段。任何生产写入、部署、切流、数据库变更、推送提交、删除旧实现均需另行授权。
7. 计划及测试证据默认仅存本地仓库，不上传公共报告服务。

## 2. 目标架构

- 新实现目录：`/root/newapi-rs/`，采用 Rust + Axum + Tokio 的模块化单体架构，Cargo workspace 按业务域分 crate，一个可部署服务，不拆微服务。`apps/server` 为 Axum composition root；`crates/identity`、`catalog`、`relay`、`billing`、`usage`、`integrations` 等按阶段创建，不预建空壳。业务域拥有自己的业务逻辑、持久化实现和测试，通过显式公开接口交互；传输层与领域逻辑分离，禁止跨模块直接读写内部表或导入私有实现。公共基础能力限于配置、数据库连接、错误/观测等稳定边界，禁止形成无边界的 common 巨型模块。P0 固定依赖图，Cargo DAG 禁止循环依赖；跨域协作用显式应用服务/端口编排。
- HTTP 中间件：Tower/Tower HTTP；JSON：Serde；上游 HTTP：Reqwest；日志与追踪：tracing。具体依赖版本在 P0 核查兼容性后锁定 `Cargo.lock`。
- 数据访问采用 SQLx，为 SQLite、MySQL、PostgreSQL 使用明确的数据库实现与方言测试；不假设任意 SQL 可以跨库通用。依赖版本能否支持当前数据库最低版本必须实测；不能满足时先提出计划修订，不静默提高门槛。
- 按 `config / transport / identity / security / catalog / relay / billing / usage / jobs / integrations / storage` 分层。路由只做协议适配，业务规则不绑定 Axum extractor，外部 HTTP/时钟等边界可替换测试。
- 前端继续使用 `apps/web`，保持现有接口路径、字段、错误响应、鉴权语义和流协议。不得以大规模修改前端掩盖兼容性问题。
- Rust 后端初期使用独立监听端口与测试数据库，不连接生产库，不主动自动迁移现有数据库。
- 保留旧数据库 schema、主键、金额/额度单位、时间戳、密码散列、令牌和软删除语义；未经确认不做破坏性 schema 重构。

## 3. 兼容性基线

P0 建立并冻结以下台账；全部实际条目应逐项映射至 P1–P9，不允许仅用下面的分类标题宣称覆盖完整。

### HTTP 与前端

逐项记录 method、path、路由优先级、鉴权/权限、中间件、请求字段/默认值、返回字段/类型、状态码、响应头、分页、错误格式、国际化、Cookie/CORS、上传限制、SSE/WebSocket 行为和对应前端调用位置。包括管理 API、AI 协议、回调、静态资源及 SPA fallback。

### 数据与一致性

记录所有表、列、索引、约束、默认值、JSON 字段、加密字段、软删除、独立日志库、迁移文件及已有版本升级行为。重点记录事务边界、锁序、缓存失效、多实例一致性、金额精度、幂等键和重试语义。

### 运维与外部依赖

记录环境变量、启动参数、Redis、后台任务、对象/文件存储、邮件、OAuth、支付、机器人、出站网络/代理、健康检查、备份、日志脱敏与前端产物打包方式。对历史已退役接口不重新实现，对现存能力不擅自删除。

## 4. 全过程阶段及验收

### P0 — 源码基线与契约清单

**交付：**记录克隆 commit；完成路由、模型、后台任务、集成、前端依赖和现有测试清单；明确各数据库版本及测试方式；建立 Go 行为基线与脱敏 fixture。检查许可证/NOTICE 义务。确定测试数据库和上游模拟器隔离方案。

**验收：**每条已注册路由和每个后台任务均有迁移阶段归属；每张业务表有读写归属；在 Actions 运行相关 Go 基线测试，不能运行则 P0 保持受阻；任何豁免须用户确认替代证据，不伪造基线通过。确认环境具备 Rust 构建和独立复核能力。

### P1 — 可运行基础与公共配置垂直切片

**交付：**建立 `Cargo.toml`、`Cargo.lock`、启动入口、配置解析、日志脱敏、错误边界、请求大小限制、优雅退出、存活/就绪检查；实现三类数据库连接与 options 读取；移植 `/api/notice`、`/api/about`、`/api/home_page_content` 的真实持久化读取，以及法律文档接口的配置映射。缺少配置与数据库错误必须区分处理；不自动创建或修改旧库。

**参考：**`apps/api/internal/transport/compose/register_api.go:19`，`apps/api/internal/transport/handler/handle_misc.go:177–235`，`apps/api/internal/dbinfra/store_options.go:42–76`。复用其字段与默认值语义而非复制 Go 实现。

**验收：**可独立启动 Axum；已迁移接口与 Go fixture 对比通过；空配置、合法配置、数据库不可用、非法环境配置、方法错误、未实现路由均有测试；三数据库集成测试分别报告结果。未实现接口不能意外进入 SPA 并返回成功页面。

### P2 — 初始化、身份认证与权限

**交付：**安装向导与管理员初始化、登录/登出、会话、密码散列兼容、注册与验证码、密码重置、用户状态校验、权限策略、管理员/普通用户隔离、API Key 验证、令牌限制、速率限制及需要的 Redis 支持。实现并发初始化防护、会话撤销与权限变更生效。完整迁移 `/api/status` 等能力声明，不能将未实现功能标为启用。

**验收：**原密码和令牌 fixture 可用；过期、撤销、禁用、跨用户越权、并发初始化、重放和限流路径覆盖；敏感信息不落日志。若现有 session 无法共享，必须先批准明确的重新登录策略。

### P3 — 管理面板业务与渠道目录

**交付：**用户/令牌管理、渠道/模型/分组/供应商、定价配置、系统设置、权限管理、导入导出、缓存刷新及渠道健康配置等现有管理路由；迁移前端所依赖的查询、分页、过滤和聚合语义。涉及资金变更的写操作明确归入 P4，本阶段只验收非资金业务；资金动作保持未实现状态，不能临时无账务更新。

**验收：**前端初始化、登录、日常管理流程贯通；三数据库 CRUD、唯一约束、软删除和授权回归通过；每项未完成动作明确失败，不返回假成功。

### P4 — 账务核心与一致性

**交付：**额度/余额、分组和模型倍率、表达式计费、价格版本、预扣/结算/退款、兑换/充值基础、订阅/套餐、用量日志与事务一致性；复用旧计费用例作为 Rust 数值金标准。明确整数/定点精度、舍入、溢出、幂等和取消处理。

**验收：**计费金标准逐项一致；并发扣费、重复回调、重复结算、请求失败、取消、断连及崩溃恢复测试通过；资金守恒与不可重复扣费不变量成立。未通过前禁止连接真实付费上游承载业务流量。

### P5 — 核心 AI 网关

**交付：**渠道选择、路由单位/健康状态、令牌与模型授权、上游凭证处理、OpenAI 兼容 models/chat/completions 等核心接口、流式 SSE、重试/超时/取消、错误映射，并接入 P4 完整账务链路。重试必须明确何时允许，已向客户端输出内容后不得盲目重放。

**验收：**模拟上游端到端验证非流式/流式；覆盖慢客户端、背压、上游错误、半途断流、客户端取消、超大响应及用量缺失策略；实际扣费与日志一致，无凭证泄漏，不将完整流缓冲成一次响应。

### P6 — 全协议与全部现有上游适配器

**交付：**按 P0 台账逐个迁移 Responses、Claude、Gemini、embeddings、图像、音频、rerank、视频、实时/WebSocket 等源码中存在的协议与渠道；协议转换、工具调用、多模态、缓存 usage、异步提交/查询/取消及计费规则一并迁移。

**验收：**每个适配器记录请求/响应 golden fixture、流式与错误用例以及完成状态；模拟器通过不等于真实供应商验收，缺少合法凭证时明确记录受阻。未经用户批准不削减适配器列表。

### P7 — 外部集成、后台任务与统计

**交付：**OAuth/OIDC/Passkey/第三方登录、支付与回调、邮件/机器人、运营集成、定时任务、渠道探测与健康恢复、配置同步/outbox、日志/统计/排行榜/看板、文件清理及其他 P0 发现的业务模块。

**验收：**回调签名、过期/重放、幂等、任务重启恢复、多实例锁和时区边界覆盖；影子实例不发送真实通知、不处理真实支付、不重复运行有副作用的任务。

### P8 — 全量兼容、安全与性能验收

**交付：**完整前端端到端测试、Go/Rust 差分测试、数据库升级/备份恢复演练、安全回归、并发/长连接/资源泄漏测试、依赖与许可证审查；审阅全部未完成项。

**验收：**路由/模块/数据台账无未批准缺口；认证、计费、租户隔离、敏感日志、上游 URL/代理和文件访问等高风险问题清零；比较相同硬件和固定负载下的吞吐、P50/P95/P99、RSS、CPU、连接和错误率。性能指标在运行前根据 Go 基线确定并记录，不能测完后调整指标制造通过。

### P9 — 构建、部署与渐进切流

**交付：**Rust release 构建、容器镜像、静态前端产物、部署配置、可观测性、配置说明、数据库备份/恢复手册与回滚运行步骤；保留 Go 部署方式。在授权环境按测试→预发布→小比例→扩大比例推进。

**验收：**构建可重复、容器健康/退出正常；预发布演练通过；每次切流前另行授权并检查错误率、账务差额、数据一致性与延迟门槛。出现资金差异、安全问题、数据破坏立即停止扩量并按经批准步骤回滚。切流前冻结共存数据协议：Go/Rust 的写入 schema 双向兼容、会话与缓存共享策略、后台任务单一执行权、在途请求 drain 与账务结算。应用回滚与数据库恢复分别设计，禁止直接恢复旧备份导致切流后交易丢失；观察窗口和量化门槛在切流前确定。

### P10 — 旧后端退役与交付

**交付：**所有必需能力验收、生产观察窗口与负责人确认、归档 Go 基线和回滚产物；用户明确批准后才删除/退役旧实现。更新构建入口、正式维护说明及最终迁移台账。

**验收：**无依赖 Go 的运行时业务路径；历史数据、升级、运维和备份恢复可持续维护；最终独立验证通过。不能用“主体完成”代替完整重写完成。

## 6. 验证规程（仅远程 GitHub Actions）

**硬性禁止本地构建、测试、启动服务及本地容器验证。** 此约束适用于主代理、所有子代理、独立验证代理与 Git hooks。下文全部构建/测试命令只允许在 GitHub-hosted Actions runner 执行。本地仅做源码阅读/编辑、静态审阅、Git/worktree 操作和 `gh` 远程操作；不得以调试、验收或复核为由绕过。

每个实现阶段在 Actions 运行 `cargo fmt --check`、`cargo check --locked --workspace`、`cargo clippy --locked --workspace --all-targets -- -D warnings`、`cargo test --locked --workspace`，并运行该阶段数据库集成与契约测试。Actions checkout 新仓库后在仓库根目录执行命令，不依赖本地绝对路径。集成测试必须证明实际连到各目标数据库，而非全数跳过。

每次非平凡实现后由独立 verification 代理审查原始需求、计划、改动文件、行为与测试，输出有执行命令及结果的 PASS/FAIL/PARTIAL；FAIL 修复后复验；PARTIAL 保持阶段受阻，不视为验收通过。主执行者通过 `gh` 触发远程复跑，抽查其中 2–3 条验证命令及对应日志，绝不在本地复跑。所有证据绑定 commit SHA、workflow run ID、环境、退出码、测试数量及跳过数量；代码改变后旧 PASS 不能直接沿用。独立验证服务不可用时明确报告阻塞，不自签通过。

涉及计费/身份/外部服务的测试使用脱敏数据和模拟上游，真实调用必须有用户授权。不将生产凭证、数据库、聊天内容或付费请求发送至第三方评审服务。

## 7. 多 Agent 独立工作区与免费 CI 工作流

1. P0 首先搭建独立新仓库和最小 CI，而非等到 P9 才有构建验证。P9 负责发布/部署流水线。通过 Git 根目录、git-dir、worktree 清单和所有 remote push URL 确认新仓库独立，且不会推送原仓库。
2. 默认同时最多 3 个开发 Agent，采用 Workflow 编排；每个写代码 Agent 使用新仓库内独立 Git worktree 和独立分支。共享目录禁止并行写入。只读探索可共用参考源码；所有写入只发生在新仓库 worktree。
3. 每阶段先确定模块契约、文件所有权及任务依赖，再并行分发可独立任务；接口、Cargo 清单/lock、公共模型、CI 文件由指定集成者负责。阶段内并行，阶段间仍遵守验收依赖，不以并行为由跳过账务/鉴权前置条件。
4. Agent 交付改动、契约测试和静态检查说明，不声称本地验证通过。集成者审查后按获得授权的 Git 策略整合到集成分支并推送新仓库，远程 CI 对集成结果验证；独立 verification 代理读取该精确 SHA 的 CI 日志并审查实现。
5. 仅使用账号确认可免费使用的标准 GitHub-hosted Linux runner；不启用 larger runner、付费服务或自托管本机 runner。确认新仓库可见性和账号额度后再冻结 runner 配置；免费额度耗尽则暂停报告，不自动付费。
6. 使用最小 `contents: read` 权限、锁定 Actions 版本、Cargo 依赖缓存、按分支 concurrency 取消过期运行及合理 timeout。普通改动先快速 fmt/check/clippy/unit，再运行受影响集成测试；阶段验收必须全量三库和契约矩阵，不能因路径过滤或跳过得出假绿。
7. 通过 `gh run list/view/watch` 获取状态与失败日志，按失败证据定向修复；不循环无意义重跑。CI 中生成并验证 Cargo.lock，随后通过受控方式回收至新仓库；不得为生成 lockfile 本地构建。Go 基线也仅在 Actions 中从固定上游 commit 检出并运行，不对上游仓库发起任何写操作。
8. 用户已明确授权：在 `gh` 当前登录账号下创建公开 `newapi-rs`，向该新仓库提交和推送开发分支以运行 CI。计划批准后先核对 `gh` 身份及同名仓库是否已存在；如已存在则停止确认，不覆盖。该授权不包含原仓库写入、force-push、生产部署、付费 runner 或真实付费上游测试。
